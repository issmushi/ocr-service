# OCR Service

Backend OCR-сервиса: единое FastAPI-приложение с API, PaddleOCR, MRZ Scanner,
RussianDocsOCR, Qwen и QR. PostgreSQL, RabbitMQ и встроенный worker
обрабатывают асинхронные задачи через `/v1/tasks`.

RussianDocsOCR установлен в окружение API и запускается его lifespan как отдельный
рабочий процесс. V1 использует его для визуальных полей внутреннего паспорта РФ.
Движок использует только ONNX. Его семь наборов весов оформлены как отдельная
модельная зависимость: в Git хранится lock-манифест, а `install.sh` скачивает
точно зафиксированный набор RussianDocsOCR `v1.0.1` и проверяет SHA-256 каждого
файла.
Отдельные HTTP-сервис, порт 8002 и Python-окружение Russian OCR не нужны.

Python-код единого приложения находится непосредственно в `app/`, а конфигурация
проекта и служебные каталоги — в корне репозитория:

```text
pyproject.toml         # зависимости и запуск приложения
poetry.lock
app/                   # Python-пакет app
  bootstrap/           # сборка приложения, HTTP и управление запуском
  core/                # общие механизмы
  modules/             # сценарии и HTTP endpoints
  ocr_engine/          # Paddle, MRZ Scanner, RussianDocsOCR
  workers/             # выполнение асинхронных задач
  main.py              # ASGI-приложение и запуск uvicorn
profiles/              # окружения CPU, GPU и VLM
tests/
alembic/
alembic.ini
```

Отдельных приложений Russian OCR и MRZ Scanner больше нет: их движки входят
в `app/ocr_engine`. Установка и управление всем стеком выполняются единым
корневым скриптом `install.sh`.

`app/main.py` экспортирует `app` и `run`. В `app/bootstrap/factory.py`
собираются маршруты и OpenAPI, в `http.py` регистрируются middleware и
обработчики ошибок, в `lifecycle.py` управляется запуск и остановка OCR,
а в `background.py` находятся периодические задачи обслуживания.
OCR-движки и их фоновые задачи принадлежат процессу API.

Для разработки установите зависимости группы `dev` и проверяйте код из
корня проекта:

```bash
poetry install --with dev
poetry run python -m app.ocr_engine.russian.assets fetch
poetry run ruff check app
poetry run ruff format --check app
poetry run pytest -q
```

Настройки Ruff хранятся в `pyproject.toml`: Python 3.11, длина строки
79 символов, проверки PEP 8, сортировка импортов и абсолютные импорты
`app.*`. Для применения форматирования: `poetry run ruff format app`.
Отложенные импорты OCR-библиотек внутри фабрик сохраняют загрузку моделей
в отдельных рабочих процессах. Внешний код RussianDocsOCR в
`app/ocr_engine/russian/vendor/` исключён из общего форматирования;
его происхождение описано в `PROVENANCE.md` внутри этого каталога.

`POST /v1/ocr/full` синхронно распознаёт весь текст одного изображения `image`
через `paddle`, `qwen3-vl-4b` или `qwen3-vl-8b` и возвращает
`data.text` и `data.meta` (`engine`, `model`, `duration_seconds`).

Шесть операций распознавания и обрезки доступны также как задачи:
`POST /v1/tasks/passport/mrz`, `/passport/page`, `/idcard/mrz`, `/full`,
`/crop/document` и `/crop/mrz`. Параметры совпадают с прямыми запросами.
Создание возвращает HTTP `202` с `task_id`; статус читается через
`GET /v1/tasks/{task_id}`, результат — через `GET /v1/tasks/{task_id}/result`.
Отмена: `POST /v1/tasks/{task_id}/cancel`.

`POST /v1/ocr/passport/mrz` принимает изображение `image`, модель `paddle`,
`mrz`, `qwen3-vl-4b` или `qwen3-vl-8b` и булевы поля формы `crop`, `normalize` и
`normalization`. По умолчанию `model=paddle`, `crop=true`, `normalize=true` и
`normalization=true`: API выравнивает документ, находит MRZ, передаёт каждому
движку только её фрагмент и возвращает журнал исправлений. При `crop=false`
движок получает исходное изображение. При `normalization=false` журнал равен
`null`. При `normalize=false` исправления и достройка отключены; остаются
удаление пробелов, uppercase и выбор строк. Из итоговой MRZ
API также возвращает тип и код паспорта, страну, ФИО, пол, даты, номер,
гражданство и доступные страновые поля.
Для всех моделей выбираются две самые длинные строки с сохранением порядка OCR.
MRZ Scanner работает на CPU и загружается при первом выборе `model=mrz`.

`POST /v1/ocr/idcard/mrz` использует те же модели и флаги для ID-карт Казахстана
(две или три строки MRZ) и Кыргызстана (три строки, `IDKGZ` или `I<KGZ`).
Ответ содержит MRZ, журнал коррекций, поля документа с `document_number` и
`document_series`, а также одинаковый `meta`. При `normalize=false` и
`normalization=true` оба MRZ-endpoint возвращают пустой журнал.

`POST /v1/ocr/passport/page` распознаёт визуальные поля страницы внутреннего
паспорта РФ через RussianDocsOCR или Qwen3-VL и возвращает их с теми же именами,
что MRZ-сценарий. Обязательное multipart-поле `page` сейчас принимает только
значение `3`: поддерживается только 3-я страница внутреннего паспорта РФ.
Оба паспортных endpoint возвращают одинаковый `meta` с полями `engine`,
`model` и `duration_seconds`.
Поля `mrz`, `normalization` и `mrz_valid` в этом ответе равны `null`.
При `crop=true` (по умолчанию) API вырезает и выравнивает весь документ без
поиска MRZ; `crop=false` передаёт движку исходное изображение.

Для отдельной обрезки доступны `POST /v1/ocr/crop/document` и
`POST /v1/ocr/crop/mrz` в группе Swagger **Crop**. Оба принимают файл `image`
и возвращают готовый JPEG: выровненный документ или найденную MRZ.
Если MRZ не найдена, второй маршрут возвращает `422 / OCR_FAILED`.

`POST /v1/ocr/best-frame` в группе **Best frame** выбирает лучший кадр документа
из нескольких файлов `image` (по умолчанию до трёх). Ответ содержит исходную
картинку без перекодирования; заголовки `X-Selected-Index` и `X-Quality-Score`
сообщают индекс и оценку. Это отдельная операция, пока не подключённая к OCR
или Tasks.

QR-модуль шифрует паспортные данные алгоритмом AES-256-GCM. Установщик при
первой установке создаёт постоянный 256-битный ключ в локальном `.env`; ключ
не записывается в QR и не коммитится в Git.

## Выбор кадра для QR

`POST /qr/decode` принимает от одного до трёх изображений. Каждый файл передаётся
повторением multipart-поля `image`. Операции распознавания и обрезки V1 принимают
одно изображение: прямые `/v1/ocr/...` возвращают результат сразу, а
`/v1/tasks/...` ставят обработку в очередь. Отдельный `/v1/ocr/best-frame`
принимает несколько кадров для выбора одного.

Перед оценкой QR-кадров API учитывает EXIF-ориентацию и создаёт уменьшенную
рабочую копию изображения с максимальной стороной `OCR_QUALITY_MAX_SIDE`
(по умолчанию `1600 px`). Исходное изображение при этом не изменяется.

### Критерии для `/qr/decode`

Для QR используется отдельная формула, потому что QR-код может занимать только
часть изображения и не обязан находиться внутри контура документа:

| Критерий | Вес |
| --- | ---: |
| Резкость | 30% |
| Отсутствие бликов | 20% |
| Экспозиция | 15% |
| Локальный контраст | 15% |
| Разрешение | 10% |
| Шум и размытие | 10% |

Полнота документа и перспектива в QR-балл не входят. API сортирует кадры по
этому баллу и проверяет их локальным QR-модулем по одному. Если на первом
кадре QR не найден или его данные повреждены, проверяется следующий кадр.
Ответ возвращается после первого успешного декодирования.

Оценка выполняется детерминированными алгоритмами OpenCV без OCR и без
обученной модели. Она оценивает пригодность изображения, но не гарантирует
наличие документа или QR-кода.

## Установка и управление

Интерактивный запуск предлагает выбрать комплектацию и устройство, показывает
итоговый план и просит подтверждение:

```bash
./install.sh
```

Доступны три комплектации:

- `standard` — PaddleOCR, MRZ Scanner и Russian OCR;
- `extended` — стандартная комплектация плюс Qwen3-VL 4B и 8B;
- `manual` — точный список моделей из `OCR_MODELS` в `.env`. Допустимые значения:
  `paddle`, `mrz`, `russian-ocr`, `qwen3-vl-4b`, `qwen3-vl-8b`.

Если выбран `russian-ocr`, установщик кладёт проверенные модели в
`storage/models/russian-docs-ocr/1.0.1/models`. Другой каталог можно задать
через `RUSSIAN_OCR_MODELS_DIR`. Для установки без интернета подготовьте полный
каталог моделей и укажите его в `RUSSIAN_OCR_MODELS_SOURCE_DIR`: установщик
скопирует только недостающие или повреждённые файлы и снова проверит их по
lock-манифесту.

Для воспроизводимой установки без диалога укажите оба выбора и `--yes`:

```bash
./install.sh --edition standard --device cpu --yes
./install.sh --edition extended --device gpu --yes
./install.sh --edition manual --device cpu --yes
```

`--device gpu` использует NVIDIA CUDA на Linux x86_64. На Apple Silicon он
ускоряет Qwen через Metal, а остальные выбранные модели работают на CPU.
Установщик проверяет backend `llama-server` перед применением GPU-профиля.
Интерактивно предлагаются только CPU и GPU. Явный `--device npu` сохранён как
диагностическая проверка: он определяет NPU и завершается с ошибкой до любых
изменений, поскольку проверенного NPU-профиля пока нет.

План можно проверить без установки и изменения `.env`:

```bash
./install.sh --edition standard --device cpu --dry-run --yes
```

По умолчанию после установки стек запускается. Флаг `--no-start` оставляет его
остановленным. Последующее управление выполняется тем же скриптом:

```bash
./install.sh start
./install.sh status
./install.sh restart
./install.sh stop
```

`stop` завершает OCR API и Qwen VLM; PostgreSQL и RabbitMQ продолжают работать
в Docker.
